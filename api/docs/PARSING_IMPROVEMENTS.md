# Улучшения логики парсинга и parser_api

## Текущая архитектура (кратко)

- **parser** (внешний сервис) — по `POST /parse` принимает `query`, `pages`, возвращает `vacancies[]`, `collected`.
- **parser_api** — создаёт `ParseJob` (pending → running → done/failed), вызывает parser, сохраняет вакансии через `VacancyRepository.upsert_many`, привязывает к пользователю через `UserVacancy`.

---

## 1. ~~Исправление бага: DailyCheckScheduler~~ (сделано)

**Было:** В `daily_check_scheduler.py` вызывался несуществующий метод `parsing_service.parse_and_ingest(...)`.

**Сделано:**
- В конфиг добавлен `daily_check_user_id: int | None` — id пользователя, к которому привязываются джоба и вакансии ежедневной проверки. Если не задан, планировщик не стартует.
- `run_parse_and_ingest` теперь возвращает `ParsingResult | None` (при успехе — результат, при ошибке — `None`).
- В `run_check_once`: создаётся джоба через `start_parse_job`, затем вызывается `run_parse_and_ingest`; при успехе отправляется отчёт в Telegram. Для работы daily check нужно задать `DAILY_CHECK_USER_ID` в окружении.

## 2. Сохранение причины сбоя в ParseJob

**Сейчас:** При `failed` в БД пишется только `status='failed'`, `finished_at`. Пользователь не видит, почему джоба упала.

**Предложение:**

- В модель `ParseJob` добавить поле `error_message: Optional[str]` (или `failure_reason`).
- В `ParsingService.run_parse_and_ingest` в блоке `except` перед `mark_job_finished(job_id, "failed")` сохранять `str(exc)` (или обрезанную версию, например 500 символов) в это поле.
- В репозитории — `mark_job_finished(job_id, status, error_message=None)`.
- В API при отдаче `ParseJobStatusResponse` добавить поле `error_message: str | None` и отдавать его на фронт (например, в карточке джобы и в списке джоб).

**Плюсы:** Удобная отладка, понятные сообщения пользователю («Парсер недоступен», «Таймаут», «Неверный ответ»).

## 3. Retry при вызове parser

**Сейчас:** Один запрос к parser; при любой сетевой/временной ошибке джоба сразу переходит в `failed`.

**Предложение:**

- В `HttpParserClient.parse` (или в `ParserOrchestrator.trigger_parse`) сделать 2–3 повтора с экспоненциальной задержкой (например 2s, 4s) только для:
  - таймаутов (`httpx.TimeoutException`);
  - 5xx и 429;
  - временных сетевых ошибок (connection error, read error).
- Не повторять при 4xx (кроме 429) и при ошибках валидации ответа.

**Плюсы:** Меньше ложных `failed` из‑за кратковременных сбоев parser/сети.

---

## 4. Ограничение одновременных джоб на пользователя

**Сейчас:** Пользователь может запустить много джоб подряд; все выполняются в фоне, возможна перегрузка parser и БД.

**Предложение:**

- Ввести лимит «активных» джоб на пользователя (например, не более 1 в статусе `pending` или `running`).
- В `ParsingService.start_parse_job` перед созданием новой джобы проверять количество таких джоб для `user_id`; если лимит превышен — возвращать ошибку (например 409 Conflict) с сообщением «Дождитесь завершения текущего парсинга».
- Опционально: лимит на количество джоб в единицу времени (rate limit) для защиты от злоупотреблений.

---

## 5. Детализация результата в ответе API и в ParseJob

**Сейчас:** В ответе `POST /jobs` возвращаются `collected=0`, `new_count=0`, `updated_count=0` (джоба только поставлена в очередь). После завершения при запросе `GET /jobs/{id}` нет полей `collected`, `new_count`, `updated_count`.

**Предложение:**

- В модель `ParseJob` добавить поля: `collected: Optional[int]`, `saved_count: Optional[int]`, `new_count: Optional[int]`, `updated_count: Optional[int]`.
- В `run_parse_and_ingest` после успешного `ingest_vacancies` вызывать расширенный `mark_job_finished(job_id, "done", collected=..., saved_count=..., new_count=..., updated_count=...)`.
- Метод `ingest_vacancies` в `VacancyService`/репозитории должен возвращать не только общее число сохранённых, но и разбивку new/updated (например, через сравнение с `list_existing_external_ids` до вставки или через RETURNING и проверку по `ingested_at`/флагу).
- В схему `ParseJobStatusResponse` и в ответ `GET /jobs/{id}` добавить эти поля (и по желанию отдавать их в списке `GET /jobs`).

**Плюсы:** Пользователь видит реальный результат парсинга (сколько собрано, сколько новых/обновлённых) без необходимости смотреть только список вакансий.

## 6. Валидация и нормализация ответа parser

**Сейчас:** Ответ parser разбирается как `data.get("vacancies")`, `data.get("collected")` без строгой схемы; возможны некорректные типы или отсутствие обязательных полей.

**Предложение:**

- Описать ожидаемую структуру одной вакансии (Pydantic-модель или dict с типами) и валидировать каждый элемент `vacancies` перед передачей в `ingest_vacancies`.
- Отбрасывать или логировать невалидные элементы; при полной невалидности всего списка можно считать джобу failed с `error_message` вида «Parser returned invalid vacancy payload».
- Нормализация: приведение типов (например, `salary_from`/`salary_to` к float), обрезка длинных полей (title, description) до разумной длины перед записью в БД.

**Плюсы:** Меньше падений и «мусорных» записей в БД при изменении формата ответа parser.

## 7. Таймаут и отмена длительных джоб

**Сейчас:** Таймаут задаётся только на HTTP-клиент (например 120 с). Если parser «висит», джоба так и остаётся в `running` до таймаута или падения.

**Предложение:**

- Явно передавать таймаут в `HttpParserClient` из настроек и при необходимости — разный для разных окружений.
- Опционально: периодическая фоновая задача (scheduler), которая находит джобы в статусе `running` дольше N минут и помечает их как `failed` с `error_message="Timeout"` (или «Превышено время выполнения»). Это защитит от «залипших» джоб при сбоях parser.

## 8. Расширение контракта с parser (по желанию)

**Сейчас:** Параметры только `query` и `pages`.

**Идеи для parser_api и parser:**

- Поддержка фильтров: `city`, `experience`, `schedule` — если parser умеет их передавать в HH API, parser_api может принимать их в `ParseRequest` и прокидывать в parser.
- Идемпотентность: опциональный `idempotency_key` от клиента, чтобы не создавать дубликаты джоб при повторной отправке формы (сохранять ключ в ParseJob или в кэш и при повторном запросе с тем же ключом возвращать существующую джобу).

## 9. Метрики и логирование

**Предложение:**

- Логировать в одном формате (структурированно): `job_id`, `user_id`, `query`, `pages`, `status`, `collected`, `saved`, `duration_seconds`, `error_message` (при failed).
- Опционально: счётчики (Prometheus) — количество запущенных/успешных/неуспешных джоб, время выполнения, количество сохранённых вакансий. Это поможет смотреть на надёжность парсинга и нагрузку.

## 10. Daily check: системный пользователь и метод

**Сейчас:** Daily check не может вызвать текущий `ParsingService`, т.к. у него нет `parse_and_ingest` и нет привязки к пользователю.

**Предложение:**

- Ввести в конфиге опциональный `daily_check_user_id` (или отдельный флаг «сохранять в общий пул»).
- Реализовать метод вида `run_daily_check_parse_and_ingest()` в сервисе, который:
  - создаёт ParseJob с `user_id=daily_check_user_id` (или без привязки к пользователю, если решите хранить «общие» вакансии отдельно);
  - вызывает parser и `ingest_vacancies` для этого user_id;
  - обновляет статус джобы и при необходимости шлёт отчёт в Telegram.
- Либо оставить текущую схему «только для одного пользователя» и в daily check использовать конкретного пользователя из настроек; тогда в `DailyCheckScheduler` создавать джобу и вызывать `run_parse_and_ingest(job_id, query, pages, user_id)`.
